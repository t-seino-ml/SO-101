# テレオペレーションのラグ調整（完了）

リーダー機とフォロワー機の追従遅れ、操作速度の差、カメラ表示のラグへの対処です。すべて実測に基づいています。

## 結論

| 症状 | 原因 | 対処 |
|---|---|---|
| 断続的な引っかかり | シリアルのパケットタイムアウトに固定 +50ms | マージンを 5ms に |
| 操作速度が実機と合わない | `max_relative_target` の速度制限と追加読み取り | 既定でオフ |
| 全体的な遅れ | 制御 120 Hz、表示が毎ステップ | 制御 200 Hz、表示 30 Hz に分離 |
| カメラ映像の遅れ | カメラが 20 fps | 原理的な下限。制御の応答とは別物 |

## 1. パケットタイムアウトの固定 +50ms

最大の要因です。LeRobot は Feetech SDK の `setPacketTimeout` にパッチを当てています。

```python
# lerobot/motors/feetech/feetech.py
self.packet_timeout = (self.tx_time_per_byte * packet_length) + (self.tx_time_per_byte * 3.0) + 50
```

末尾の `+ 50` が固定マージンです。パケットが 1 回落ちるたびに読み取りが約 50ms ブロックし、制御が止まります。1 Mbaud での 6 サーボ sync_read は約 0.5ms なので、100 倍の余裕を取っていることになります。

`hardware/bus_patch.py` でこの関数を差し替え、マージンを 5ms にしました。10 秒間・120 Hz での実測です。

| マージン | 達成 Hz | control 最大 | 20ms 超のステップ |
|---|---|---|---|
| 50ms（LeRobot 既定） | 108 Hz | 103.01 ms | 20 件（1.8%） |
| **5ms（採用）** | 119 Hz | 7.51 ms | 0 件 |
| 2ms | 119 Hz | 4.97 ms | 0 件 |

リトライ回数（10 / 3 / 1）を変えても最大値は 52ms のまま変わりませんでした。リトライの累積ではなく、**1 回のタイムアウトそのもの**が原因だと確認できます。

`SO101_PACKET_TIMEOUT_MS` で変更できます。小さくしすぎると健全な読み取りまで失敗するため、5ms を既定としました。

## 2. `max_relative_target` のコスト

安全のための 1 ステップあたり移動量の上限ですが、2 つのコストがあります。

- **速度制限そのもの** — 5° に設定すると、200 Hz でも 1000°/秒が上限になります
- **追加のフォロワー読み取り** — 現在位置を知る必要があるため sync_read が 1 回増えます。LeRobot のコードにも "Slower fps expected due to reading from the follower" と明記されています

実測で control の中央値が 1.32ms → 2.26ms とほぼ倍になりました。**既定でオフ**にしています。初回起動時のみ `--max-relative-target 5` を推奨します。

## 3. 制御と表示の分離

LeRobot の `teleop_loop` は 1 イテレーションで、フォロワーの状態読み取り、リーダー読み取り、指令送信、そして**カメラ画像を含む観測全体の rerun への送信**をすべて行います。

`so101/teleop.py` では 2 つのレートに分けました。

- **制御（毎ステップ）** — リーダー読み取り → フォロワーへ送信。シリアル 2 往復で約 1.25ms
- **表示（既定 30 Hz）** — フォロワーの状態と最新フレームを読み、rerun へ送信。1 回 3.4ms

表示 1 回あたりのコスト実測です（ビューアなし、メモリシンク）。

| 内容 | 中央値 |
|---|---|
| 関節のみ | 0.17 ms |
| 関節 + 800x600 画像 2 枚 | 1.44 ms |

## 4. 制御レートを 200 Hz に

制御が 1 ステップ 1.2ms で済むため、レートを上げる余地があります。実測では 400 Hz まで安定して回りました。

| fps | 達成 | 周期 中央値 | 周期 p95 |
|---|---|---|---|
| 120 | 120 Hz | 8.34 ms | 8.34 ms |
| **200（採用）** | 199 Hz | 5.00 ms | 5.01 ms |
| 300 | 297 Hz | 3.34 ms | 3.34 ms |
| 400 | 396 Hz | 2.50 ms | 2.51 ms |

200 Hz を既定にしました。1 ステップあたり 3.8ms の余裕が残り、カメラ 2 台と表示を動かしても崩れません。`FPS=300 ./scripts/teleop.sh` で変更できます。

## 最終実測（カメラ 2 台・表示あり・200 Hz）

```
1991 steps in 10.0s (199 Hz achieved, 200 Hz asked)
  control  median 1.25 ms   p95 1.61 ms   max  7.78 ms   (1991 calls)
  display  median 3.44 ms   p95 4.16 ms   max  9.19 ms   (249 calls)
  period   median 5.00 ms   p95 5.01 ms   max 10.42 ms   (budget 5.00 ms)
```

50ms 級の停止は消え、p95 が予算とほぼ一致しています。

再現は `scripts/bench_teleop.py` で行えます。ビューアを起動せずメモリシンクへ記録するため、ループ自身のコストだけが測れます。

## カメラ映像のラグについて

**制御の応答とは別物です。** カメラは 800x600 MJPG で約 20 fps、1 フレーム 50ms です。これに取得パイプラインと rerun ビューアの遅延が加わります。

解像度を下げても 20 fps は変わりません（[docs/02-camera.md](02-camera.md) の実測参照）。USB 帯域の制約で 2 台同時には 800x600 が上限のため、現状これが下限です。

## 切断時のトルク解除

`Robot.disconnect()` は関節を 1 つずつ解除し、**最初の書き込み失敗で中断します。** それ以降の関節はトルクが入ったまま残ります。

負荷がかかった直後のサーボは、書き込み自体は成功していてもステータスバイトにエラーを返すことがあり、LeRobot はそれで例外を投げます。そのため書き込みの成否は判定に使えません。

`teleop.release_torque()` は全関節に対して試行し、**レジスタの読み戻し**（ステータスバイトで例外を投げない経路）で確認します。`teleop_view.py` は切断失敗時にこれを呼びます。

可動域の端で長時間保持すると過負荷保護がかかりやすくなります。テレオペ終了時は、無理のない姿勢にしてから停止してください。
